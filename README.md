# mlops-batch-pipeline
A minimal MLOps-style batch pipeline demonstrating reproducibility, observability, and deployment readiness using Python and Docker
 It loads a YAML config, reads an OHLCV CSV,
computes a rolling-mean signal on `close`, and writes structured metrics
(JSON) plus a detailed run log.

> **Note on `data.csv`**: the dataset linked in the task spec lives in a
> private Google Sheet that isn't reachable without sign-in. The
> `data.csv` included here is a deterministic synthetic OHLCV dataset
> (10,000 rows, seed 42, generated by `gen_data.py`) with the same shape —
> `timestamp, open, high, low, close, volume`. Swap in the real file at
> any time; `run.py` only depends on a `close` column existing.

## What it does

1. Loads and validates `config.yaml` (`seed`, `window`, `version`)
2. Sets `numpy.random.seed(seed)` for reproducibility
3. Loads and validates the input CSV (exists, non-empty, valid CSV, has `close`)
4. Computes a rolling mean of `close` over `window` rows
5. Derives a binary signal: `1` if `close > rolling_mean`, else `0`
   (the first `window - 1` rows have no full window and are excluded from
   the signal / `signal_rate` calculation — consistent NaN handling)
6. Writes `metrics.json` (always, success or failure) and `run.log`
7. Prints the final metrics JSON to stdout and exits `0` on success,
   non-zero on failure

## Local run

```bash
pip install -r requirements.txt

python run.py \
  --input data.csv \
  --config config.yaml \
  --output metrics.json \
  --log-file run.log
```

No paths are hard-coded — all four arguments are required and taken as-is,
so the job can be pointed at any config/input/output location.

## Docker

Build:

```bash
docker build -t mlops-task .
```

Run:

```bash
docker run --rm mlops-task
```

The image bundles `data.csv` and `config.yaml` and runs the exact CLI above
internally, so `docker run --rm mlops-task` alone reproduces the full job:
it writes `metrics.json` and `run.log` inside the container, prints the
final metrics JSON to stdout, and exits `0` on success / non-zero on
failure.

To pull the output files back out to your host, mount a volume instead of
relying on the container's ephemeral filesystem, e.g.:

```bash
docker run --rm -v "$(pwd)/out:/app/out" mlops-task \
  python run.py --input data.csv --config config.yaml \
  --output out/metrics.json --log-file out/run.log
```

## Example `metrics.json` (success)

```json
{
  "version": "v1",
  "rows_processed": 10000,
  "metric": "signal_rate",
  "value": 0.4991,
  "latency_ms": 32,
  "seed": 42,
  "status": "success"
}
```

## Example `metrics.json` (error)

```json
{
  "version": "v1",
  "status": "error",
  "error_message": "Input CSV is missing required column: 'close'"
}
```

## Error handling

`run.py` validates and reports on, without a stack trace reaching stdout:

- Missing input file
- Empty input file
- Invalid / unparseable CSV
- Missing `close` column
- Invalid or incomplete config (missing `seed` / `window` / `version`,
  wrong types, non-mapping YAML)

In every case a `metrics.json` with `status: "error"` and a human-readable
`error_message` is still written, the full exception is logged to
`run.log`, and the process exits with a non-zero code.

## Reproducibility

Given the same `config.yaml` (same `seed`, `window`) and the same
`data.csv`, `signal_rate` and `rows_processed` are exactly reproducible
run-to-run. `latency_ms` will naturally vary with machine load.
